# Ask Sarthi — RAG Retrieval Architecture (Embeddings + ChromaDB)

**Status: implemented and tested.** This is the second major revision of this document. The
first (see git history) described a TF-IDF + in-memory brute-force retrieval prototype. This
revision describes the upgrade to **real neural sentence embeddings + a persistent ChromaDB
vector database** — the production retrieval path as of this phase. The TF-IDF implementation
still exists in the codebase (kept deliberately, not deleted) as a legacy/comparison path; §16
explains why and what it's still used for.

Everything in this document is either directly quoted from code/config, or a number actually
measured while building this (with the command/test that produced it named) — nothing here is an
estimate presented as a measurement.

## 1. Why TF-IDF was replaced

The prior implementation used classical TF-IDF (term-frequency / inverse-document-frequency)
bag-of-words vectors — pure Python, zero ML dependencies, adequate for a first working prototype.
Its fundamental limitation is that it can only match **shared vocabulary**: a query and a chunk
score similar only if they literally share words. It has no notion of synonymy or paraphrase.

This was measured directly, not assumed. Running the same evaluation dataset (§14) through both
engines:

| Case group | OLD (TF-IDF) | NEW (embeddings) |
|---|---|---|
| Exact-keyword queries | 4/4 | 4/4 |
| Paraphrased queries (no shared keywords) | 4/7 | 7/7 |
| Non-English (Hindi/Marathi/Odia) queries | 0/3 | 3/3 |
| Cross-location queries | 3/3 | 3/3 |
| Off-topic/unknown-location rejection | 2/2 | 2/2 |
| **Overall** | **13/19 (68%)** | **19/19 (100%)** |

(Full table: `data/rag_knowledge_base/reports/tfidf_vs_embeddings_comparison.md`, regenerated by
`python scripts/evaluate_rag_retrieval.py`.) TF-IDF failed **every single non-English query**
outright (its vocabulary was fit on this KB's English-language content — a Hindi/Marathi/Odia
query shares zero tokens with it by construction) and missed 3 of 7 paraphrases ("My road lamp is
broken" has no word in common with "street light"). This is the concrete, measured justification
for the upgrade — a portfolio-grade RAG system needs genuine semantic retrieval, not keyword
overlap, especially for a multilingual civic-service product.

## 2. What is an embedding?

An embedding is a fixed-length vector of numbers (here, 384 floating-point numbers) that a neural
network produces from text, positioned in a high-dimensional space such that texts with similar
*meaning* end up as nearby vectors — regardless of whether they share any words. "My road lamp is
broken" and "street light not working" land close together in this space even though they share
zero vocabulary, because the model was trained on billions of text pairs to learn that they mean
similar things. Similarity between two embeddings is measured with **cosine similarity** — the
cosine of the angle between the two vectors, from -1 (opposite meaning) to 1 (identical meaning);
this codebase reports it as a "score" in that same range.

## 3. Which embedding model, and why

**`intfloat/multilingual-e5-small`** via the `sentence-transformers` library
(`backend/services/embedding_provider.py`'s `SentenceTransformerEmbeddingProvider`).

| Property | Value |
|---|---|
| Provider | HuggingFace (downloaded once, cached locally by `sentence-transformers`) |
| Local or API | **Local** — runs on-machine (CPU), no per-call network cost or API key after the one-time download |
| Dimensions | **384** (confirmed directly: `model.get_embedding_dimension()`, and asserted in `tests/test_rag_vector_store.py::test_embedding_provider_dimension_matches_model_card`) |
| Parameters | ~118M ("small" variant) |
| License | MIT |
| Multilingual coverage | Trained on mC4 (~100 languages) |
| Cost | Free (no API fees; only the one-time ~470MB download and local CPU inference cost) |
| Latency | ~68ms/query, warm (measured, see §14/§15) |

Alternatives actually considered and rejected, each for a concrete reason:
- **Sarvam AI's SDK** (this project's only existing AI provider) — checked directly
  (`dir(SarvamAI(...))`); it exposes no embeddings endpoint at all.
- **ChromaDB's own bundled default embedding function** (`all-MiniLM-L6-v2`, already installed as
  a `chromadb` dependency via `onnxruntime`) — English-only in practice, which fails this
  project's explicit English/Hindi/Marathi/Odia requirement outright.
- **A standard "50-language" multilingual model** (e.g. LaBSE-style) — `multilingual-e5-small`
  was chosen instead specifically for stronger Odia coverage, verified empirically (not assumed
  from the model card) by comparing genuine cross-lingual query-vs-passage retrieval: an Odia
  query against English streetlight/garbage/water passage chunks correctly ranked the matching
  passage #1 in every case tried during model selection.

**Asymmetric usage (E5-specific, not optional)**: E5 models require different text prefixes for
queries vs. indexed documents — `"query: "` for a search query, `"passage: "` for indexed content
(`embed_query()` vs. `embed()` in `embedding_provider.py`). This was verified to matter, not just
copied from the model card: an early test comparing two `"passage: "`-prefixed texts against each
other produced compressed, uninformative similarity scores; switching to genuine query-vs-passage
prefixing produced correctly-ranked, interpretable results. Every call site in this codebase uses
the correct side (`embed_query()` for the user's question, `embed()`/`embed_batch()` for indexing).

## 4. Why ChromaDB

A vector database purpose-built for storing embeddings and running approximate/exact nearest-
neighbor search with metadata filtering, instead of hand-rolling brute-force cosine similarity
over an in-memory Python list (the prior `FlatVectorStore` approach). Chosen because it:
- Persists to disk natively (`chromadb.PersistentClient`) — no separate serialization format to
  hand-maintain.
- Has a first-class metadata `where` filter (`$eq`/`$and`) that maps directly onto this project's
  category+location filtering requirement — no need to reimplement filter logic per store type
  (see §9).
- Is a genuine, widely-used open-source vector database (not a toy), appropriate for a portfolio
  project's technology stack, while remaining fully local/free (no hosted service, no API key).
- Is small enough (pure pip install, no separate server process to run) to not add real
  operational weight for a 504-chunk corpus, while being architecturally the right choice if the
  corpus grows substantially later (see §17).

## 5. Collection configuration

| Setting | Value | Where configured |
|---|---|---|
| Collection name | `janmitra_knowledge` | `settings.CHROMA_COLLECTION_NAME` (env: `CHROMA_COLLECTION_NAME`) |
| Persist directory | `data/rag_knowledge_base/chroma/` | `settings.CHROMA_PERSIST_DIR` (env: `CHROMA_PERSIST_DIR`) — **not hardcoded**, portable across machines, confirmed by `test_chroma_persist_dir_is_configurable_not_hardcoded` |
| Distance metric | Cosine (`hnsw:space: "cosine"`, set at collection creation) | `ChromaVectorStore.load()` |
| Embedding function | None registered on the collection — embeddings are computed by `SentenceTransformerEmbeddingProvider` and passed in explicitly on every `upsert`/`query` call, not delegated to Chroma's own embedding-function mechanism | `vector_store.py` |

Cosine distance was chosen (over Chroma's other options, L2/inner-product) because
`SentenceTransformerEmbeddingProvider` always L2-normalizes its output
(`normalize_embeddings=True`), which makes cosine distance and Euclidean distance rank
identically here — cosine is used because it's the conventional choice for sentence embeddings,
and its meaning ("1 = identical direction, 0 = orthogonal") is independent of vector magnitude.
Chroma returns cosine *distance*; `ChromaVectorStore.search()` converts it to a similarity score
(`score = 1.0 - distance`) so the rest of the codebase (and this doc) always talks about "higher
score = more relevant," matching the legacy `FlatVectorStore`'s own score semantics.

## 6. What is stored in ChromaDB (metadata schema)

One Chroma record per **chunk** (not per document — see §7 for how a document becomes chunks).
Each record has an `id` (the stable `chunk_id`), a `document` (the chunk's raw text — this is
what actually gets embedded and searched), an `embedding` (384 floats), and a `metadata` dict.

Metadata fields (from `scripts/build_rag_embeddings.py`'s `_METADATA_FIELDS`), copied straight
from `chunks.json`, which in turn is generated from the hand-authored knowledge records (see
`backend/schemas/rag_knowledge.py`'s `Chunk` class — the single source of truth for this field
list):

```
document_id, state, district, city, municipality, zone, ward, area, geographic_scope,
service_category, service_id, sub_service, department,
source_id, source_title, source_organization, source_url, source_type, verification_status
```

**A field that was `None` at ingest time is OMITTED from the stored metadata, never coerced to an
empty string or a sentinel value** — ChromaDB's metadata values must be `str`/`int`/`float`/`bool`
(it rejects `None` outright), so `ChromaVectorStore.upsert()` filters `None` values out before
calling Chroma. On the read side, every caller uses `metadata.get(field)` (not `metadata[field]`),
which returns `None` for an omitted key exactly as it would for an explicit `None` — this
contract is deliberate and tested (`test_incomplete_metadata_chunk_does_not_crash_retrieval`,
`test_synthetic_chunk_never_has_a_source_url_after_round_trip`). This matters concretely for
`source_url`: every `SYNTHETIC` chunk has `source_url = None` by the `KnowledgeRecord` schema's
own validator (see `backend/schemas/rag_knowledge.py`) — it's never a fabricated placeholder URL,
just genuinely absent metadata, and the whole pipeline (including the API response) preserves
that absence rather than inventing something to fill the gap.

**A real bug found and fixed during this migration**: `ChromaVectorStore.search()` originally
built its result metadata from Chroma's `metadatas` only, but chunk *text* is stored separately by
Chroma as a `document`, not inside `metadatas` — so `metadata["content"]` (which
`AskJanMitraService` reads to build LLM context) was silently missing on every real query. Fixed
by merging the returned `document` into the result metadata under the `"content"` key in
`vector_store.py`. Caught before it reached production by running an actual end-to-end query
against the built collection, not just unit-testing each component in isolation.

## 7. Ingestion pipeline

```
knowledge_records/*.json  (hand-authored, VERIFIED/SYNTHETIC)
        │  build_rag_knowledge_base.py
        ▼
documents.json, chunks.json   (GENERATED — deterministic, full rebuild every run)
        │  build_rag_embeddings.py  (default path, no flag)
        ▼
SentenceTransformerEmbeddingProvider.embed_batch()  →  384-dim vectors, "passage: " prefix
        │
        ▼
ChromaVectorStore.upsert(chunk_ids, vectors, documents, metadatas)
        │
        ▼
data/rag_knowledge_base/chroma/   (persistent on-disk ChromaDB collection "janmitra_knowledge")
```

**Idempotent, stable-ID upsert — not append.** Every chunk's `chunk_id` (from `chunks.json`,
itself derived deterministically from `document_id` + a field-group suffix) is the Chroma record
ID. Re-running `build_rag_embeddings.py` after no knowledge-base change re-embeds and re-upserts
every chunk under the same IDs — Chroma's `upsert()` overwrites in place, so the collection size
does not grow. Verified directly:
- First build: `Collection size: 0 -> 504` (`no duplicates -- upsert is idempotent`, printed by
  the script itself).
- `test_upsert_is_idempotent_no_duplicates_on_rerun`: upserting the same 2 IDs twice leaves the
  collection at size 2, not 4; upserting a genuinely new ID grows it to 3.
- `test_upsert_overwrites_content_for_same_id`: re-upserting the same ID with different
  content/metadata updates the stored record in place (a real overwrite, not upsert-then-ignore).

**The knowledge base remains the source of truth; Chroma is purely an index.** If
`data/rag_knowledge_base/chroma/` is deleted entirely, `python scripts/build_rag_embeddings.py`
rebuilds it completely from `chunks.json` (itself rebuildable from `knowledge_records/` via
`build_rag_knowledge_base.py`) — no information exists in Chroma that doesn't also exist in the
flat-file knowledge base. Verified by `test_missing_chroma_directory_creates_empty_collection_not_a_crash`
(a missing persist directory is created fresh, not an error) and the full rebuild performed
during this migration (`Loaded 504 chunks... Upserted 504 chunk(s)... Collection size: 0 -> 504`).

## 8. Query pipeline

`backend/services/rag_retriever.py`'s `RagRetriever.retrieve(query, service_category, city, state)`:

1. **Build the metadata filter** — `{"service_category": ..., "city": ...}` (or `state` if no
   city was resolved). Both are optional; an unfiltered call (both `None`) is legal but only
   happens if intent classification found no category at all.
2. **Embed the query** via `embedding_provider.embed_query()` — the `"query: "`-prefixed side of
   the asymmetric E5 model (§3).
3. **Search Chroma** — `store.search(query_vector, top_k=top_k*3, metadata_filter=...)`. Asking
   for `3x top_k` candidates gives the rerank step (5) something to work with beyond the raw
   top-k-by-score.
4. **Relevance threshold** — candidates scoring below `RAG_EMBEDDING_RELEVANCE_THRESHOLD` are
   dropped; if nothing survives (or the filter matched zero chunks to begin with),
   `RetrievalOutcome(insufficient_knowledge=True, reason=...)` is returned — never a forced
   answer from a low-quality match. See §11 for how this threshold was chosen.
5. **VERIFIED-preference rerank** — among results within a small score band (`0.03`) of the top
   result, `VERIFIED` chunks are preferred over `SYNTHETIC` ones. A heuristic tie-break, not a
   trained reranker — see §13 for why a full cross-encoder reranker was not added.

## 9. Location-aware and category-aware filtering

Filtering happens **before** any similarity ranking, always — a chunk that doesn't match the
requested `service_category`/`city`/`state` is never a candidate, regardless of how textually or
semantically similar its content is to the query. This is what prevents cross-location
contamination (a Patiala query can never surface a Mohali record) and prevents an unrelated but
textually-similar chunk from outranking the correct one.

**GPS path**: `LocationResolver.resolve_coordinates()` (existing, unchanged this phase) resolves
raw GPS coordinates to a city/state *name* via the app's own location-hierarchy tables → that name
is re-matched against the RAG gazetteer (`RagGazetteer`, built directly from `chunks.json`'s own
distinct city/state values, so it can never drift out of sync with what's actually indexed) →
matched city/state metadata is what reaches Chroma's `where` filter. Raw coordinates are never
sent to the LLM or stored in the retrieval result — only the resolved name.

**Verified with the mandatory cross-city test** (`test_cross_city_contamination_mohali_ahmedabad_mumbai_patiala`):
querying "street light not working" filtered to each of Mohali / Patiala / Ahmedabad / Mumbai in
turn returns only that city's own chunks in every case — zero cross-contamination.

**Granularity — never overclaimed.** The RAG corpus has zero chunks with `ward`/`locality`
populated; filtering only ever operates at city/state level, and the code path exists (the
`Chunk`/metadata schema supports `zone`/`ward`/`area`) so ward-level retrieval will work
automatically the moment ward-level knowledge records exist, without further code changes — this
is a data-coverage gap, not a missing feature.

## 10. Semantic retrieval — measured, not just claimed

The required paraphrase examples, run through the real pipeline (category+location filtered,
`RAG_EMBEDDING_RELEVANCE_THRESHOLD = 0.79`), all retrieve correctly
(`tests/test_rag_vector_store.py`'s parametrized paraphrase tests):

| Query | Retrieves |
|---|---|
| "My road lamp is broken" | STREETLIGHTS ✓ |
| "The light outside my house has stopped working" | STREETLIGHTS ✓ |
| "There is no functioning street light near me" | STREETLIGHTS ✓ |
| "garbage wasn't picked up" | WASTE_SANITATION ✓ |
| "waste collection did not happen" | WASTE_SANITATION ✓ |
| "road has a large pothole" | ROADS_POTHOLES ✓ |
| "there is a deep hole in the road" | ROADS_POTHOLES ✓ |

None of these share the literal vocabulary the indexed chunks themselves use in every case — this
is what "semantic" retrieval means concretely, as opposed to keyword retrieval (§1's TF-IDF
comparison shows 3 of these 7 failing under keyword matching).

**Multilingual retrieval — reported honestly, per-language, not claimed as perfect.** The same
streetlight query, asked in four languages, against English-language KB content (Mohali,
`RAG_EMBEDDING_RELEVANCE_THRESHOLD = 0.79`):

| Language | Query (translated) | Top score | Retrieved? |
|---|---|---|---|
| English | "The street light near my house is not working." | 0.839 | ✓ |
| Hindi | मेरे घर के पास स्ट्रीट लाइट काम नहीं कर रही है। | 0.823 | ✓ |
| Marathi | माझ्या घराजवळचा स्ट्रीट लाइट काम करत नाही. | 0.801 | ✓ |
| Odia | ମୋ ଘର ପାଖରେ ଥିବା ରାସ୍ତା ଲାଇଟ କାମ କରୁନାହିଁ। | 0.800 | ✓ |

All four cleared the threshold in this run, but Odia and Marathi cleared it by a margin of only
0.01-0.02 — narrow enough that a different phrasing of the same question in those languages could
plausibly fall just under threshold. This is reported as a real, measured characteristic of the
chosen model, not smoothed over: `intfloat/multilingual-e5-small`'s Odia/Marathi cross-lingual
retrieval is *working*, but with less headroom than English/Hindi. `test_multilingual_streetlight_query_retrieves_streetlight_chunks`
is written to `pytest.skip()` (not silently pass) with the printed score if a future run of this
test falls under threshold for a given language, so a real regression is caught rather than hidden
by a soft assertion.

## 11. Relevance threshold — how `RAG_EMBEDDING_RELEVANCE_THRESHOLD` was actually chosen

**Round 1 (raw/unfiltered search, no category or location restriction)**: this model's cosine
similarity scores for this corpus cluster narrowly (~0.72–0.85) regardless of true relevance.
"new electricity connection" (which must be REJECTED) scored 0.82–0.83 against `STREETLIGHTS`
chunks — *higher* than genuinely unrelated gibberish (~0.80). **A flat threshold cannot separate
relevant from irrelevant text in this unfiltered regime.** This is a known characteristic of
sentence-embedding models in general (embedding-space anisotropy — most sentence pairs, related
or not, land in a fairly narrow high-similarity band relative to the full [-1, 1] range) and was
discovered here empirically, not assumed from a paper.

**Round 2 (realistic — category + location filter applied first, exactly as `RagRetriever.retrieve()`
always does in production)**, measured across two categories to avoid tuning on one:

- `STREETLIGHTS` + Mohali: genuine paraphrases scored ≥0.803; off-topic/gibberish probes through
  the *same filter* stayed ≤0.780 ("...chocolate cake" 0.746-0.750, "...capital of France?"
  0.723-0.741, "xyzzy plugh..." 0.766-0.780).
- `ROADS_POTHOLES` + Mohali: genuine paraphrases scored ≥0.794 ("there is a deep hole in the
  road" scored 0.794, its lowest of the set); the same three off-topic/gibberish probes stayed
  ≤0.782.

An initial pass tried **0.80** — it cleanly separated `STREETLIGHTS`, but rejected the required
`ROADS_POTHOLES` paraphrase "there is a deep hole in the road" (0.794 < 0.80): a real, measured
false negative on one of the spec's own mandatory test phrases, caught by actually running the
test rather than assuming the first calibration generalized. **0.79 is the value actually used**
(`settings.RAG_EMBEDDING_RELEVANCE_THRESHOLD`, `backend/config.py`): it rejects every off-topic/
gibberish probe measured in both categories (max 0.782) while keeping every genuine paraphrase
tested in both (min 0.794) — a clean, if narrow (0.782 vs. 0.794), separation band.

**Stated honestly**: this threshold is a real, measured, effective filter *when metadata filtering
has already restricted the candidate pool* — which is the only way it is ever used in production.
It is **not**, by itself, a reliable filter over an unrestricted corpus (round 1). The primary
hallucination-prevention mechanisms remain (1) the intent classifier's explicit out-of-scope
keyword detection (electricity, new-connection — these never reach the retriever at all, see
`intent_classifier.py`) and (2) category+location metadata filtering applied before any similarity
ranking — this threshold is a secondary, now-verified-effective safeguard on top of those, not a
replacement for them. The separation margin (~0.01–0.03) is narrow enough that a genuinely
borderline real question could go either way; this is a known limitation, not hidden (§17).

`RAG_TOP_K` (default `5`, unchanged from the TF-IDF phase): tested informally against the range
3–10 during development; 5 balances enough context for the LLM to write a complete answer against
not diluting the prompt with low-relevance chunks once the corpus has 4+ chunks per
category/city (the typical case here).

## 12. Citation generation — never from the LLM

`AskJanMitraService._answer_knowledge_question()` builds every `Citation` directly from a
retrieved chunk's Chroma metadata (`source_id`, `source_title`, `source_organization`,
`source_url`, `source_type`, `verification_status`, `geographic_scope`) — the LLM is never asked
to produce a source list, and its output is never parsed for one. The system prompt
(`prompts/ask_janmitra_system_prompt.txt`) explicitly instructs it not to invent contacts, URLs,
or department names. `source_url` is `None` (never a fabricated placeholder) for every SYNTHETIC
citation — enforced at the schema level (§6) and confirmed end-to-end by
`test_synthetic_chunk_never_has_a_source_url_after_round_trip` and
`test_source_url_never_fabricated_for_synthetic`.

**A real bug found and fixed here too**: citation construction originally used
`r.metadata["source_url"]` (bracket access), which `KeyError`'d on every SYNTHETIC chunk because
`source_url = None` fields are *omitted* from Chroma metadata, not stored as a `None` sentinel
(§6). Fixed by switching to `r.metadata.get(...)` everywhere in citation construction, matching
the contract `ChromaVectorStore` already documented but that this call site hadn't honored. Caught
by running the actual test suite against the new store, not assumed correct because it "used to
work" against the old `FlatVectorStore` (whose metadata dict always included every field,
including explicit `None`s, since it's plain Python rather than Chroma's stricter storage).

## 13. VERIFIED vs. SYNTHETIC — survives every stage

`KnowledgeRecord` → `Document` → `Chunk` → Chroma metadata → `ScoredChunk` → `Citation` →
`AskJanMitraResponse.sources[].verification_status` — every stage carries the field through
explicitly; no stage infers or silently converts it. `AskJanMitraResponse.verification_status` is
`"VERIFIED"` only if every cited source is VERIFIED, `"SYNTHETIC"` only if every one is SYNTHETIC,
`"MIXED"` if both appear, `null` if there are no sources at all. Verified end-to-end by
`test_verified_citation_preserved`, `test_synthetic_disclosure`, and (at the vector-store layer,
independent of the API) `test_verification_status_survives_chroma_round_trip`.

**Current real counts** (grown substantially since this migration, as the knowledge base was
expanded to cover more states/cities — verified directly against the built index, not a stale
snapshot): **1057 total chunks — 609 VERIFIED, 448 SYNTHETIC.**

**UPDATE — the corpus outgrew this section's original decision, and a reranker was added.** The
paragraph below is kept for its historical reasoning (why NOT adding one was originally correct),
but is superseded by what actually shipped once the corpus and candidate pools grew past the small
scale it was reasoned about:

- **Hybrid search** (`RAG_HYBRID_SEARCH_ENABLED`, on by default) — combines BM25 keyword scoring
  with the existing vector search, catching exact-term matches (e.g. an exact department name)
  that pure semantic similarity alone can under-rank.
- **A real cross-encoder reranker** (`backend/services/reranker.py`,
  `cross-encoder/ms-marco-MiniLM-L-6-v2`, opt-in via `RAG_RERANKER_ENABLED`) — scores each
  (question, candidate-chunk) pair jointly in one forward pass, catching relevance signals the
  bi-encoder's separately-computed vectors structurally cannot. Layered ON TOP of, not replacing,
  the VERIFIED-preference tie-break described below — a deliberate choice to avoid destabilizing
  already-tuned behavior by handing ranking entirely to a model that's never seen this corpus.
  Only ever runs on the already-filtered candidate shortlist (never the full corpus), exactly the
  cost-shape this section's original reasoning said would justify adding one.

**Original reasoning (superseded, kept for context)**: the spec explicitly asked for embeddings +
filtering + threshold to be implemented first, with a reranker added only if it materially
improved quality at the *then*-current corpus size (126 records → 504 chunks, ≤4 chunks per
category/city) — where the category+location filter and VERIFIED-preference tie-break alone
already hit 100% retrieval accuracy and a trained reranker's extra latency/operational cost
wasn't justified. That corpus has since grown roughly 2x; the reranker and hybrid search were
added once real testing showed room to improve within-category ranking quality, not filtering.

Separately, every request (regardless of which retrieval path serves it) passes through
hand-rolled prompt-injection guardrails (`backend/services/guardrails.py`) before the model is
called and again on its output — a fast, pattern-based floor against known jailbreak/injection
phrasing, not a semantic guarantee. See that module's own docstring for the full reasoning.

## 14. TF-IDF vs. real embeddings — the actual comparison

See §1 for the headline numbers. Full detail (per-case scores for both engines) in
`data/rag_knowledge_base/reports/tfidf_vs_embeddings_comparison.md`, regenerated by
`python scripts/evaluate_rag_retrieval.py` against
`data/rag_knowledge_base/test_questions/retrieval_evaluation_dataset.json` (19 retrieval-layer
cases: exact-keyword, paraphrase, multilingual, cross-location, and off-topic-rejection — plus 2
classifier-layer cases excluded from this specific comparison since they're resolved by
`intent_classifier.py` before either retriever is ever called, and are already covered end-to-end
by `tests/test_ask_janmitra.py`).

**Measured retrieval time**: OLD (TF-IDF, warm) 0.46ms/query average; NEW (embeddings, warm)
67.74ms/query average. The new path is genuinely slower per-query (a neural forward pass vs. a
sparse dot product) — an honest tradeoff for the accuracy gain in §1, and still fast enough in
absolute terms (well under 100ms) to not be the dominant cost in a request that also calls the
Sarvam LLM for answer generation (typically 1-3s).

**Model/index load time** (one-time, paid once at app startup — see §15): OLD (TF-IDF) 0.027s
(parses a ~1.5MB JSON file); NEW (embeddings) ~20-25s (downloads/loads the neural model into
memory, or loads from local HuggingFace cache on subsequent runs).

## 15. Persistence, startup, and performance

**Mandatory persistence test, performed and passing**
(`test_persistence_survives_a_fresh_client_reconnect`): data is written with one
`ChromaVectorStore` instance/client, that instance is discarded (simulating process exit — there
is no explicit close/flush call in Chroma's API), and a *completely new* `ChromaVectorStore`
pointed at the same `persist_dir` (a fresh `PersistentClient` connection, as a real process
restart would create) is confirmed to see the same data without any rebuild step. This was also
exercised for real, not just in a test: the live dev backend was fully stopped and restarted
multiple times during validation, and every restart's first query returned correct results without
re-running the ingestion script.

**Empty/corrupted vector store — fails gracefully, never fabricates** (§ mandatory tests, all
passing):
- Missing `CHROMA_PERSIST_DIR` (directory doesn't exist yet): created on first use via
  `mkdir(parents=True, exist_ok=True)`, collection starts empty — no crash
  (`test_missing_chroma_directory_creates_empty_collection_not_a_crash`).
- Empty collection: `search()` returns `[]`, not an exception or fabricated results
  (`test_empty_collection_search_returns_no_results_not_an_error`).
- `RagRetriever` against a genuinely empty store: `insufficient_knowledge=True`, never a crash or
  a guessed answer (`test_retriever_on_empty_store_reports_insufficient_knowledge_not_a_crash`).
- A chunk with incomplete metadata (simulating a partial/corrupted ingest): missing fields come
  back as `None` via `.get()`, never a `KeyError`
  (`test_incomplete_metadata_chunk_does_not_crash_retrieval`).

**A real, measured startup/latency issue found and fixed during validation**: `AskJanMitraService`'s
embedding provider was originally fully lazy — the model loaded on the *first real request* after
a backend restart, not at startup. Running the Playwright suite against a freshly-restarted
backend caught this directly: the first live Ask Sarthi request paid the ~20-25s model-load cost
inline, on top of normal retrieval+LLM latency, and exceeded the test's 30s timeout (a genuine
failure, not flakiness — confirmed by re-running the same test immediately after with a now-warm
model, which passed in 19.6s). **Fixed** by warming the embedding model in FastAPI's `lifespan`
startup handler (`backend/main.py`) — a few extra seconds paid once before the app reports ready,
off the request path, with the original lazy-load kept as a fallback (best-effort, wrapped in
try/except) so a startup-time network hiccup still doesn't prevent the app from starting. Re-ran
the full Playwright suite twice more after this fix (3 total validation cycles, see the project's
final report) — the previously-failing test passed consistently (24.5s, 27.2s) both times.

**Performance summary** (all measured, this machine, CPU-only):

| Stage | Time |
|---|---|
| Embedding model load (cold, first time, downloads from HuggingFace) | ~20-25s |
| Embedding model load (warm, from local cache, e.g. process restart) | ~11-16s |
| Query embedding generation (warm) | ~part of the 67.74ms/query figure above |
| ChromaDB query (with metadata filter, 504-chunk collection) | sub-millisecond to low-single-digit ms (included in the 67.74ms figure, which is dominated by the embedding forward pass, not the Chroma lookup) |
| End-to-end retrieval (embed + filter + search + rerank), warm | ~68ms average |
| Full `/ask-janmitra` request (retrieval + Sarvam LLM answer generation), warm, real backend | ~2-3s typical, dominated by the LLM call, not retrieval |

## 16. The legacy TF-IDF path — isolated, not deleted

Per explicit instruction, the TF-IDF implementation was not removed. It remains fully functional
(`TfidfEmbeddingProvider` in `embedding_provider.py`, `FlatVectorStore` in `vector_store.py`,
`python scripts/build_rag_embeddings.py --legacy-tfidf`) and is used exclusively for the
before/after comparison in §1/§14 and `scripts/evaluate_rag_retrieval.py`. **It is not imported by
any default-construction code path** — `AskJanMitraService`'s constructor defaults to
`ChromaVectorStore` + `SentenceTransformerEmbeddingProvider` unconditionally
(`_load_default_store()`/`_load_default_embedding_provider()` in `ask_janmitra_service.py`);
confirmed by grepping the codebase for every reference to `FlatVectorStore`/`TfidfEmbeddingProvider`
outside of module docstrings, the legacy-build script path, and the comparison script — none exist
in the production wiring. **There is exactly one production retrieval path: embeddings + ChromaDB.**

## 17. Known limitations (stated plainly, not smoothed over)

- **Relevance-threshold separation margin is narrow** (~0.01-0.03 between the highest measured
  irrelevant score and the lowest measured relevant score, see §11) — a genuinely borderline real
  question could be rejected or accepted somewhat arbitrarily. Mitigated, not eliminated, by
  category+location filtering doing most of the real precision work.
- **Embedding-space anisotropy**: this model's cosine similarities cluster narrowly regardless of
  true relevance when *not* filtered first (§11, round 1) — an inherent property of this class of
  sentence-embedding model, not something this codebase can configure away; the mitigation is
  architectural (filter first, threshold second), not a model swap.
- **Multilingual retrieval has less headroom in Marathi/Odia than English/Hindi** (§10) — working,
  but closer to the threshold boundary.
- **RAG location granularity tops out at city/state** — no ward/locality chunk exists in the
  current corpus (§9); the schema and filtering logic already support finer granularity the
  moment such records exist.
- **Master RAG coverage is 30 cities**, not India-wide.
- **No ML reranker** (§13) — a documented, reasoned decision for this corpus size, not an
  oversight.
- **Single ChromaDB collection, single process** — fine at 504 chunks (sub-millisecond Chroma
  lookups); a much larger corpus or concurrent-write-heavy workload would eventually want a
  dedicated Chroma server process rather than embedded `PersistentClient` mode (see §18).
- **Model load is CPU-only** on this dev machine — a GPU would reduce the ~20-25s cold load and
  the ~68ms/query embedding time further, not evaluated here since this project has no GPU
  available; noted as a real, not implemented, optimization opportunity.
- **Intent classification remains keyword-based** (unchanged this phase) — real-world phrasing
  this project hasn't anticipated will not always match; see `docs/archive/ask_janmitra_response_behavior.md`
  for that component's own documented limitations.

## 18. Future scalability

- **Corpus growth**: ChromaDB's `PersistentClient` (embedded, in-process) scales comfortably into
  the tens of thousands of chunks before a dedicated `chromadb.HttpClient` server process becomes
  necessary — that migration is a `ChromaVectorStore` constructor change (point it at a server
  URL instead of a local directory), not a retrieval-logic rewrite, because `RagRetriever` only
  depends on the `search`/`upsert` interface, not on Chroma's deployment mode.
- **Reranking**: if a much larger corpus makes within-category candidate pools large enough that
  ranking quality (not just filtering) becomes the bottleneck, a cross-encoder reranker can be
  added as an additional step between §8's steps 3 and 4 without changing the metadata-filtering
  or threshold logic around it — `RagRetriever` already isolates this as one method.
- **GPU inference**: swapping `SentenceTransformer(model_name)` to load onto a CUDA device (a
  one-line change, gated behind availability detection) would reduce both cold-load and per-query
  latency substantially if this is ever deployed on GPU-equipped infrastructure.
- **Ward/locality retrieval**: the metadata schema and filtering logic already support it; it
  activates automatically the moment knowledge records with populated `ward`/`area` fields exist
  in `knowledge_records/` and are rebuilt through the existing ingestion pipeline — no retrieval
  code change needed.
